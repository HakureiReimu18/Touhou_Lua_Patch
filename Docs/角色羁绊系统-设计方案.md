# 角色羁绊系统（装束组合 → 增益）设计方案

> **路线（最终）**：**C#，住进 `CSharp/Shared` 的独立插件**（命名空间 `Touhou.Synergy`），
> 形态与 `BondPlugin`（绑定护符）/ `HomingPlugin`（追踪弹）一致。
> 配置为「每个内容包各放一份 `Config/synergy_config.xml`」，扫描全部启用包按加载顺序合并。
>
> **实现状态**：`CSharp/Shared/SynergySystem.cs` 已写完并通过离线编译校验（双端）；
> `Config/synergy_config.xml` 模板已就位；**尚未进游戏实测**（见 §7 待办）。
>
> 为什么最终不用 Lua（虽然可行）：Lua 侧读 XML 的路是通的（LuaCs 默认库把 `System.Xml.Linq`
> 注册成了全局），但 C# 这边**配置扫描 + XML 解析 + 每帧挂点 + 控制台指令**四件套在本仓库都有现成先例
> 可以直接照抄，零未知；判定负载虽是 0.5 秒级、Lua 也扛得住，但 C# 留了余量，
> 将来要接伤害管线 / HUD 也不用搬家。代价是逻辑改动需要重新编译（见 §6.1）。

## 1. 背景与现状

### 1.1 现在要加一组羁绊，得动什么

现有唯一做法是事件系统：`Events/Touhou_Talents_Event.xml` 里用
`CheckAfflictionAction`（`:544`）配合 `<Conditional>`（`:561`）判定，再加一套效果节点。
每加一组羁绊 = 一个新事件 + 一组条件 + 目标标签 + 概率/触发时机，且事件何时触发、
`TargetTag="crew"` 选谁、能否重复触发都要单独推敲。羁绊一多，事件文件会迅速失控。

**本方案把它压缩成"写一段 XML"。**

### 1.2 已经躺在项目里的现成素材（关键）

每件装束在 `OnWearing` 里都会**每 0.5 秒给自己刷一个身份 affliction**：

```xml
<!-- 东方潜渊行动组测试/Items/Clothes/Merry_gear.xml:158 -->
<StatusEffect type="OnWearing" target="Character" Interval="0.5" disabledeltatime="true">
    <Conditional IsBot="false"/>
    <Affliction identifier="Touhou_Merry_Character_Effect" strength="50"/>
</StatusEffect>
```

实测扫描（`Items/Clothes/*.xml` + `Items/Touhou_Mod_Linkage/*.xml`）：

| 事实 | 数值 |
|---|---|
| 会刷身份 aff 的装束文件 | **46 个**（40 角色装束 + 6 联动角色），全表见附录 A |
| 刷新节奏 | 一律 `Interval="0.5"` |
| 身份 aff 定义参数 | `duration="1.0"`、`maxstrength="10"`（46 个全部一致）；装束施加强度 50（少数 100） |
| 同一角色多套装束 | 共用**同一个**身份 aff（`Hong_Meirin_gear` / `Hong_Meirin_Plus` 都刷 `Touhou_Hong_Meirin_Character_Effect`） |
| bot 例外 | 5 件装束带 `Conditional IsBot="false"`：Akyuu / Aya / Merry / Renko / Shinki，穿在 bot 身上**不产生**身份 aff |

这个 aff 就是天然的"某某角色在场"信号：穿着期间每 0.5 秒被续命，脱下后最长 1 秒自动消失。
项目里已经在这么用了：`Lua/Scripts/Server/Renko_Red_Spot_Freak_Report.lua:301` 靠
`Touhou_Merry_Character_Effect` 判断"同船有梅莉"。

> 派生 aff 别混用：`Touhou_Marisa_Character_Effect_Hat`、`Touhou_Kokoro_Character_Effect_Mood01`、
> `..._Check`、`..._60CD` 这类是**由主 aff 派生的状态**。配置里当"成员标记"的一律是主 aff
> `Touhou_X_Character_Effect`。

### 1.3 和现有"羁绊护符"（`Bond*.cs`）的区别

`CSharp/Shared/Bond*.cs` 是**玩家自选两两配对、伤害共担**，靠护符物品驱动、配对对象任意。
本系统是**装束身份组合自动成立**的羁绊，两者互不干扰、可并存，但别复用同一批 affliction 名字。

## 2. 目标与非目标

**目标**

1. 加/改一组羁绊 = 在 XML 里加一个 `<Synergy>`（+ 需要新数值时加一个 affliction 定义）。
2. 支持 2 人及 2 人以上成员；支持"只给其中某一人"、"每个成员各拿一份"、"同船全队都吃"。
3. 中途换装、加入、死亡、重生、掉线自动跟随（周期性判定，不做一次性判定）。
4. 服务端权威，联机同步交给 affliction 系统，纯客户端不跑逻辑。
5. 其他模组可各自扩展自己的羁绊，不碰本模组的文件。

**非目标**

- 不改伤害/命中管线（有需要时在同一个插件里扩展，见 §6.1）。
- 不做 GUI 面板、不做存档（羁绊状态不落盘，靠装束身份 aff 即时推导）。

### 3.2 两个必须记住的 affliction 行为

1. **`ApplyAffliction` 会按 `100 / MaxVitality` 缩放强度** → 施加后要手动写回目标强度。
   项目既有写法见 `Renko_Red_Spot_Freak_Report.lua:101`、`Meiling_Qi_Talent.lua:78`
   （Lua 侧）与 `BondDamage.cs:285`（C# 侧的等价补偿）。
2. **重复施加同一条 aff** = 强度累加（被 `maxstrength` 截断）+ `duration` 刷新。
   本系统每 0.5 秒刷新一次并在施加后写回强度，所以最终强度恒等于配置值。

## 4. 方案设计

### 4.1 文件与结构

| 文件 | 内容 |
|---|---|
| `CSharp/Shared/SynergySystem.cs` | 全部实现：`SynergyPlugin`（插件入口）、`SynergyTickPatch`（0.5 秒节拍）、`SynergyConfig`（多包扫描 + 解析 + 校验）、`SynergyEngine`（判定与发放）、`SynergyLog` |
| `Config/synergy_config.xml` | 本模组的配置（带完整注释与三个示例，默认全部注释掉）；其他模组在各自包放同名文件 |
| `东方潜渊行动组测试/Touhou_Character_Afflictions.xml` | 增益本体（新羁绊需要新数值时才加，模板见 §4.5） |

插件卸载/重载：`Dispose()` 里移除 Hook、移除指令、`UnpatchSelf()`、清运行时状态；
`OnLoadCompleted` 里 `UnpatchSelf()` 后再 `PatchAll`，防 `reloadlua` 堆叠。

### 4.2 配置 XML schema

```xml
<Synergies>
  <Synergy id="reimu_marisa" scope="same_sub" alive_only="true" mode="while_present">
    <Member aff="Touhou_Reimu_Character_Effect"/>       <!-- 或 item="装束 identifier" -->
    <Member aff="Touhou_Marisa_Character_Effect"/>
    <Grant aff="Touhou_Synergy_ReimuMarisa_Reimu"  to="member:1"/>
    <Grant aff="Touhou_Synergy_ReimuMarisa_Marisa" to="member:2" strength="1"/>
  </Synergy>
  <Synergy id="reimu_marisa" remove="true"/>            <!-- 别的包想关掉这条 -->
</Synergies>
```

| `<Synergy>` 属性 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `id` | 字符串 | 必填 | 全局唯一；同 id 由加载顺序靠后的包整条覆盖 |
| `priority` | 整数 | `0` | **越大越优先**；多条羁绊同时成立时按它裁决（见下方"互斥裁决"） |
| `exclusive` | `none` / `members` / `all` | `none` | `none` = 可与其他羁绊同时生效；`members` = 与**共用成员**的羁绊互斥；`all` = 与任何成立的羁绊互斥。别名：`true` = `members`，`false` = `none` |
| `scope` | `same_sub` / `same_team` / `anywhere` | `same_sub` | 成员之间（以及 `crew` 目标）的范围要求 |
| `alive_only` | `true` / `false` | `true` | false = 尸体/昏迷也算在场 |
| `detect` | `crew` / `players` / `any` | `crew` | 谁能算成员：`crew` = 玩家 + 玩家队人类船员（含 AI 船员）；`players` = 只认玩家操控的角色；`any` = 不限（含中立/敌对角色）。只影响**成员检测**，不影响 `crew` 投放目标 |
| `mode` | `while_present` / `round_start` | `while_present` | `round_start` = 开局 10 秒窗口内成立即锁定，目标快照续命到巡回结束 |
| `remove` | `true` | — | 删除同 id 条目，不需要子元素 |

**互斥裁决（每拍执行）**：把本拍成立的条目按 *优先级降序 → 配置顺序升序* 排序，依次贪心选入；
与**已选中**的条目冲突的跳过（本拍不发放，已发过的增益会被撤销，条件恢复后再自动发回）。冲突定义：

- 两条中任一条 `exclusive="all"` → 冲突；
- 两条都是 `none` → 永不冲突（可无限叠加）；
- 其余情况（至少一条是 `members`）→ **共用至少一个成员角色**才算冲突。

典型用法：`红魔馆全员`（5 人，`priority="10" exclusive="members"`）与 `蕾米+芙兰`（2 人，`priority="1" exclusive="members"`）
——五人在场时前者压制后者，只有姐妹俩时后者单独生效；而成员完全不重叠的两条羁绊（如红魔馆 vs 主角组）无论怎么配都互不影响。

| 子元素 | 属性 | 说明 |
|---|---|---|
| `<Member>` | `aff` 或 `item`（二选一） | 至少 2 个有效成员，否则整条跳过 |
| `<Grant>` | `aff`（必填）、`to`（默认 `members`）、`strength`（默认 1） | `to` = `member:N` / `members` / `crew` |

### 4.3 多包扫描与合并语义

```
顺序 = ContentPackageManager.RegularPackages（按加载顺序，即创意工坊列表顺序）
逐个包：Path.Combine(pkg.Dir, "Config", "synergy_config.xml") → File.Exists → XDocument.Load

合并规则：
  · 不同 id        → 追加
  · 同 id          → 后加载的整条覆盖（members/grants 一起替换），打日志
  · remove="true"  → 删除已收集的同 id 条目
  · 解析失败 / 文件缺失 / 字段非法 → 只跳过该条或该成员，打警告继续，绝不影响其他羁绊
```

加载时机：插件 `OnLoadCompleted`、每次 `roundStart`、控制台指令 `synergy_reload`。
首次运行若本模组配置文件不存在，会自动生成一份带注释的模板。

### 4.4 判定与发放（`SynergyEngine`）

```
每 0.5 秒（SynergyTickPatch → SynergyEngine.Tick，0.5 秒节流，与装束身份 aff 同拍）：
  ① 候选角色：遍历 Character.CharacterList，滤掉 Removed
  ② 在场索引：对每个候选角色，只查配置里出现过的成员标记（watched 集合，RebuildWatched 预建）
       · aff 成员  → GetAffliction(aff).Strength > 0
       · item 成员 → 查内/外衣槽的物品 identifier
  ③ 逐条判定（while_present）：
       · 逐个成员位取一个互不重复的角色（同一角色不能占两席），并按条目的 detect 过滤
         （players = 只认玩家 / crew = 玩家 + 玩家队人类船员 / any = 不限）
       · scope 过滤（same_sub 以第 1 个成员所在潜艇为锚；都为 null = 都在艇外也算同处）
       · 成立 → 按 grants 投放：member:N 给指定成员 / members 给每个成员 / crew 给同船玩家队
               → ApplyAffliction + 写回强度 + 记进 granted[角色] = {羁绊 id → 下次刷新时刻}
                 （续命按 RefreshInterval 节流，未到点不碰 API，见 §5.2）
       · 不成立 → 对该条目此前发过的角色 RemoveAfflictions（只删本引擎发的那条），清记账
  ④ round_start 模式：
       · 开局 10 秒窗口内一旦成立 → 把当拍的目标快照进 lockedTargets[id]，之后只给这批目标续命
       · 窗口外成立不了就不成立；锁定后脱装/换人不撤销，直到 roundEnd
  ⑤ 记账清理：角色 Removed 时从 granted 里摘掉
```

**关键实现点**

- **只认自己发的那条**：`RemoveAfflictions(a => a.Identifier == aff)` 按 affliction 名字过滤，
  所以增益 aff 必须**羁绊专用**，别和装束/天赋复用名字。
- **强度写回**：`ApplyAffliction` 之后 `GetAffliction(prefab.Identifier)?.SetStrength(strength)`，
  强度还会先被 `prefab.MaxStrength` 截断。
- **施加肢体**：`AnimController?.MainLimb`（与项目其他脚本一致）。
- **兜底**：增益 aff 定义里仍建议带 `duration="2.0"` —— 万一引擎没跑（比如补丁挂点失效），
  增益会在 2 秒内自己过期，不会永久残留。

### 4.5 增益 affliction 模板（内容模组侧）

```xml
<Affliction identifier="Touhou_Synergy_ReimuMarisa_Reimu" name="羁绊·灵魔"
            type="Touhou_Character_Affliction" isbuff="true" limbspecific="false"
            maxstrength="1" duration="2.0" hideiconafterdelay="false"
            iconcolors="255,255,255;255,255,255;255,255,255;255,255,255">
    <Effect minstrength="0" maxstrength="1">
        <StatValue stattype="MeleeAttackMultiplier" value="0.1"/>
        <!-- 其余数值照常写在这里：技能、抗性、移速、生命上限皆可 -->
    </Effect>
    <Icon texture="%ModDir%/Images/Afflictions/xxx.png" sourceref="..." sourcerect="0,0,128,128"/>
    <Description textidentifier="afflictiondescription.Touhou_Synergy_ReimuMarisa_Reimu" minstrength="0" maxstrength="1"/>
</Affliction>
```

配一条文本（`Texts/ChineseAfflictionText.xml` 等四语）：

```xml
<afflictionname.Touhou_Synergy_ReimuMarisa_Reimu>羁绊·灵梦与魔理沙</afflictionname.Touhou_Synergy_ReimuMarisa_Reimu>
<afflictiondescription.Touhou_Synergy_ReimuMarisa_Reimu>……</afflictiondescription.Touhou_Synergy_ReimuMarisa_Reimu>
```

要点：`duration` 必须有（自过期兜底）；`maxstrength` ≥ 配置里的 `strength`；`isbuff="true"` 才有增益显示。

### 4.6 时序与边界

1. **不能用"开局判定一次"**：装束身份 aff 有约 0.5 秒施加延迟（`Renko_Red_Spot_Freak_Report.lua:32` 原话），
   且中途可以脱换装束。默认 `while_present` 周期性判定；`round_start` 也是"开局 10 秒窗口内检测到就锁定"。
2. **同艇锚点**：`same_sub` 以第 1 个成员为锚，其余成员须与它 `Submarine` 相同（都为 null 也成立）。
3. **item 型成员**：走 `Inventory.GetItemInLimbSlot(InnerClothes / OuterClothes)`。
   推荐优先用 aff 判定——同一角色多套装束共用同一身份 aff，按物品判定会漏掉 Plus / Eclipse / 头饰变体；
   头饰类装束不在内外衣槽，**只能**按 aff 判定。
4. **bot 装束**：5 件带 `IsBot="false"` 的装束不给 bot 身份 aff（§1.2），这些角色的羁绊对 bot 队友不成立；
   要让 bot 也能触发，就去掉对应 XML 里那行 `Conditional`。
5. **联机**：判定与施加只在服务端上下文执行（`GameMain.NetworkMember != null && !IsServer` 直接返回）；
   affliction 变化由引擎同步给客户端，客户端不跑逻辑。
6. **打断链的即时性**：条件不成立时引擎会主动移除；即使移除失败，`duration` 也会在 2 秒内兜底过期。
7. **冲突**：只移除自己发过的 aff（`granted` 记账 + 名字过滤），其他系统给的同名 aff 不受影响。

## 5. 性能

### 5.1 负载画像

判定每 0.5 秒跑一次，成本只有两块：

| 环节 | 成本 | 说明 |
|---|---|---|
| 在场扫描 | `候选角色数 × 该角色自身 aff 数` 次哈希查找 | **与配置里有几条羁绊无关** |
| 发放/续命 | 每个（羁绊 × 目标）每 `RefreshInterval` 秒一次施加 | 稳态下多数 tick 为零调用 |

### 5.2 热路径上的两个坑（已修）

1. **`CharacterHealth.GetAffliction(Identifier,bool)` 每次调用都会分配闭包 + 委托**。
   反射 IL 验证：它 `newobj` 一个编译器生成的闭包显示类，再 `newobj` 一个
   `Func<Affliction,bool>`，然后拿这个谓词扫该角色的全部 affliction。
   若按"每个候选角色 × 每个监视标记"逐个调它，就是每 tick 数百次堆分配 + 数百次全量谓词扫描。
   **改法**：改用 `CharacterHealth.GetAllAfflictions()` —— IL 只有
   `ldfld afflictions` + `callvirt get_Keys()` + `ret`，**零分配**，直接给出该角色身上全部 affliction；
   每个角色只遍历一次自己的列表，用 `Dictionary<Identifier,int>` 判断是不是监视中的标记，
   命中就按槽位号 `Add` 进对应列表（数组索引，不再有字典查找）。
2. **每 tick 重复施加增益**。原本每个已发放目标每 tick 都 `ApplyAffliction` + `GetAffliction` + `SetStrength`
   （3 次 API 调用 + 1 个 `Affliction` 分配）。**改法**：按时间节流——记账里存"下次刷新时刻"
   （`Timing.TotalTime` 基准），`RefreshInterval = clamp(prefab.Duration × 0.5, TickInterval, 2s)`；
   未到期直接返回，一次 API 都不调。`duration="2.0"` 的增益因此每 2 个 tick 才续一次；
   `duration` 缺省（常驻增益）用 2 秒做低频校验。2 秒上限保证增益被外部手段清掉后最多 2 秒补回。

其余零分配细节：`candidates` / `picked` / `buffer` 与各槽位列表都是模块级复用、每拍 `Clear()`；
移除谓词在每个增益 aff 上**预建一次**并缓存（不再每次断链新建闭包）；热路径上的调试字符串
一律先 `if (SynergyConfig.Debug)` 再拼接。

### 5.3 可验证：内置耗时计数

`SynergyEngine` 用 `Stopwatch` 统计每次判定的耗时，`synergy_list` 会打印一行摘要
（采样次数 / 平均 µs / 最大 µs / 上次候选人数）；`synergy_reload` 时清零。
据此可以在实机里直接确认开销，而不是靠估算。

### 5.4 量级参考

- 配置解析只在加载 / `roundStart` / `synergy_reload` 发生，条目数量级是几十，
  `XDocument.Load` 开销可忽略（homing 每次 `roundStart` 也这么做）。
- 对照组：若用 Lua 实现，同规模约 0.3~2 ms/tick（MoonSharp 跨语言调用是微秒级），也能接受；
  选 C# 的理由是零未知与余量（§3.3），而上面两条优化把 C# 侧的开销进一步压到了"每 tick 几百次
  哈希查找 + 零分配"的量级。

## 6. 风险与开放问题

1. **动 `CSharp/Shared` 会连累同程序集的其他系统**：词缀（`Mod.cs` / `HarmonyPatches.cs`）、
   绑定护符（`Bond*.cs`）、追踪（`Homing*.cs`）编译进同一个程序集，一处语法错误全废。
   缓解：独立文件 + 独立命名空间 + 独立 Harmony 实例；每次改完跑离线编译校验（§8）。
2. **tick 挂点依赖反射解析**：`GameMain.Update` 取不到时退到 `GameServer.Update`；
   两边都取不到会打警告并且羁绊不生效（不会崩）。**专用服务器场景未实测**（§7）。
3. **`RemoveAfflictions(predicate)` 与 `SetStrength` 写回未实机验证**（API 已核实为 public，
   但实际效果要在游戏里确认：断链后增益是否立刻消失、强度是否等于配置值）。
4. **成员 aff 依赖人工挑选**：46 件装束里存在 `_Hat`/`_Mood`/`_Check` 等派生 aff，附录 A 已列全主 aff。
5. **bot 覆盖缺口**：5 件 `IsBot="false"` 装束（§4.6 第 4 条）。
6. **"船员"语义**：`crew` 目标只认"玩家队 + 同潜艇/同队"。囚犯/游客/被俘角色是否算，
   取决于 `IsOnPlayerTeam`，实测时确认。
7. **其他模组的 XML 质量**：解析失败/字段缺失一律"跳过 + 打警告"；合并语义写进了模板注释。
8. **未做**：羁绊生效时的聊天/弹窗提示（可选扩展，见附录 B）。

## 7. 实施步骤

1. ✅ `CSharp/Shared/SynergySystem.cs`：插件骨架、tick 挂点、多包配置扫描与合并、校验、
   判定与发放、`round_start` 锁定、指令注册（`synergy_reload` / `synergy_list`）。
2. ✅ `Config/synergy_config.xml`：带注释的模板 + 三个示例（默认注释掉）。
3. ✅ 离线编译校验：双端（client / server）编译通过，产物含全部 `Touhou.Synergy.*` 类型（§8）。
4. ⬜ **进游戏实测（优先）**：
   - 启动日志应出现「角色羁绊插件已加载」与「配置已加载：文件 N（扫描包 M）…」；
   - 先在内容模组里定义一对示例增益 aff（含 duration），把示例条目取消注释；
   - 穿齐两件装束 → 增益出现；脱掉任意一件 → 2 秒内消失（并确认是否即时）；
   - 中途换装、死亡、重生、巡回重开各验一遍；
   - 验 `GetAffliction` 写回后的强度是否等于配置值（`synergy_list` + 状态栏图标）。
5. ⬜ 联机实测：listen server + 专用服务器（后者重点验 tick 挂点是否生效）。
6. ⬜ 批量补羁绊：按附录 A 填条目；需要新数值的 affliction 一并加定义 + 四语文本。
7. ⬜ 其他模组兼容验证：在另一个内容包放一份 `Config/synergy_config.xml`，
   验多包合并、同 id 覆盖、`remove="true"`。

## 8. 离线编译校验（怎么做、为什么这么做）

```powershell
# 用仓库自带的检查脚本（注意：compile-check.ps1 缺 BOM，PowerShell 5.1 会解析失败，
# 用同目录下带 BOM 的副本 _compile-check-bom.ps1）
powershell -NoProfile -ExecutionPolicy Bypass -File _dev\tools\_compile-check-bom.ps1
```

**但它默认引用的是普通游戏目录的 `Barotrauma.dll`，会满屏 CS0051**（`Item` / `Character` 是 internal，
公开成员暴露它们即报错，且既有文件也会一起报）。正确做法是引用 **Publicized** 版：

```
E:\SteamLibrary\steamapps\workshop\content\602960\2559634234\Publicized\{Barotrauma.dll, BarotraumaCore.dll}
```

其余引用（`MonoGame.Framework.Windows.NetStandard.dll` / `XNATypes.dll` / `0Harmony.dll` /
`Farseer.NetStandard.dll`）仍取游戏目录；输出程序集名保持 `InternalsAwareAssembly`。
按这个配置跑，客户端（定义 `CLIENT;DEBUG`）与服务端（定义 `DEBUG`）两遍都应通过。

## 附录 B：后续扩展

- **三人及以上**：继续加 `<Member>`（模板示例已给）；分档可用多条 `id` 递进的条目。

- **成立提示**：成立/断开时给成员发聊天或弹窗（联机私聊 / 单机 MessageBox 的先例见
  `Touhou_Costume_Pack.lua` 的 `notify`）。
- **羁绊图鉴**：指令 `synergy_list` 已能打印全部条目；要做成面板可参考 `BondGui`。
- **伤害管线联动**：需要"某羁绊成立时改伤害/命中触发"时，直接在 `SynergyEngine` 里挂标记位，
  由 `HarmonyPatches.cs` 里已有的伤害补丁读取（与词缀系统同一套做法）。
